# Changelog

## Unreleased

- Example site: import jobs, and a script that clicks through the admin. `apps/payload-example` now turns the plugin's `imports` option on over a new `sources` upload collection that only a curator can read, add to, change or delete, so nobody else can fetch a source file by its address. The seed adds a job waiting to be run and one that failed on purpose, both over made-up files; a job doesn't run when it is made. Uploaded files go in a throwaway folder that is deleted when the site stops (`EXAMPLE_UPLOADS` names a folder to keep instead). The smoke test goes from 58 to 74 checks. New `pnpm click-through` builds the site, opens a Chrome already on the machine with no window and a throwaway profile, signs in as the made-up curator and does a curator's work on all four panels, 40 checks; it installs nothing, needs the network for Payload's code editor, fails on any other request off the site, and isn't in CI.
- Payload plugin: three things that script found in the real admin (changes the unreleased plugin). The panels' paragraphs and lists sat flush against each other, because the panel's margin reset outranked its spacing rule; jsdom doesn't lay out, so no test saw it. The reset now carries no weight and the import panel's status and message are spaced too. The form under a panel repeated it: a snapshot's label, id, version, checksum and counts, and an import job's message, checksums, diagnostics, warnings and progress (three of them in Payload's code editor) are now hidden in the form with `admin.hidden`, still in its data, the API and the list's columns. And the "Made-up example data" tag touched the source's title. The docs said every button asks first; running an import never did, and they now say so.
- Payload plugin: a snapshot's content is read only when it is asked for by name (changes the unreleased plugin). A stored snapshot can be 15 MB, and Payload read all of it for every list, every relationship it filled in and every admin page. Now a read, create, update or delete that names no `select` answers with every field except `snapshot`; `select: { snapshot: true }`, REST `?select[snapshot]=true` or GraphQL's `select: true` gives the content, and the export endpoint is as before. A caller's own `select` is left exactly as asked. In the admin the content field is on the new-snapshot form only: a stored snapshot's page is sent without the content and without the JSON editor, and Payload's own Save there sends the status alone. Hosts' code that read `doc.snapshot` from a plain read, or from the document an after-read or after-change hook is given, has to select it. The lock on sealed content doesn't depend on this. Fixed on the way: the admin panels showed the old status after Payload's own Save; they now read from the site again whenever Payload reports the document saved. Tested: 10 new tests (8 on a real Payload with an in-memory MongoDB, one of them over HTTP, and 2 in jsdom), 3 new checks over HTTP in the example site (58 in all), and five deliberate breaks, each caught. Also run in headless Chrome on the example site, outside CI: a stored snapshot's page has no content and no editor, a sealed snapshot pasted into the new-snapshot form is stored with the same checksum, and Payload's Save sends one small request. Not explained: in that run, after a snapshot was made through the form and its page loaded again, Payload's read-only Counts group showed no fields under its heading; four shorter runs of the same steps drew them. Not tested: Postgres, SQLite, a browser with a window. See [ADR 0012](docs/architecture/adr/0012-payload-plugin.md), point 17.
- Payload plugin, part 5 of M7: admin panels (still not on npm). Each of the plugin's four collections gets a panel at the top of its edit page, on unless `admin: { panels: false }`. The snapshot panel says the status in words, what the snapshot holds (counts, a line per classification and phylogeny, sources with their licenses) and, for one made by accepting a proposal, which proposal and the two sealed person ids; a manager gets Publish and Withdraw. The view panel draws the saved view (the first 200 nodes) with the same tree as an outline for the keyboard and the lines readers are told, and holds Publish, with the reason, until the form is saved and the snapshot is published. The import panel shows the steps of a run, its warnings and diagnostics, looks again every 3 seconds while a job runs, and offers to run a queued, failed or interrupted job. The proposal panel says what a proposal would change, and a manager accepts it (naming the new version) or declines it. Publish, Withdraw, Accept and Decline ask first in the page and say what can't be undone (running an import doesn't ask: it stores at most a staged snapshot); accepting lists what gets sealed for good and asks the manager to check it for personal details. The panels have no powers of their own: they call the host's site from the browser as the signed-in person, so the host's `access` callbacks decide, and a refusal reads "Nothing was changed." with the site's reason. New: the `@captiveorigins/payload-plugin-onetaxonomy/client` entry (found through Payload's import map, so run `payload generate:importmap` after adding the plugin), the `admin.panels` option, and one endpoint, `GET /api/<snapshots>/:id/summary` (and `summarizeSnapshot`), which answers counts and capped lists, never names or trees, with the same 404 as the other endpoints. For a snapshot made from a proposal it gives the name the host shows for each sealed id to signed-in requesters only, looked up per request and never stored. `@payloadcms/ui` and `react` are new optional peer dependencies, and the plugin now depends on `@captiveorigins/onetaxonomy-react` for the drawing. Colours come from Payload's theme variables; a test reads the installed `@payloadcms/ui` stylesheets and checks text at 4.5:1 and control edges at 3:1 in light and dark, and a status is never colour alone. The example site shows the panels to its curator and turns Payload's Gravatar avatar off. Tested: 94 new tests (74 render the panels in jsdom with Payload's hooks and `fetch` replaced by stand-ins, 11 on the stylesheet, 9 on the summary against a real Payload with an in-memory MongoDB), and 8 new checks over HTTP in the example site (55 in all). The snapshot, view and proposal panels were also clicked through once in headless Chrome on the example site, in light and dark; that run is not in CI. Not tested: the import panel in a real admin, a screen reader, Safari, Firefox, a phone, or a custom Payload theme. Found on the way and written in the README: Payload's own admin loads its JSON editor from cdn.jsdelivr.net and, unless `admin.avatar` is `'default'`, asks gravatar.com with a hash of the signed-in person's email address. See [ADR 0012](docs/architecture/adr/0012-payload-plugin.md), point 16.

It uses a throwaway profile that it deletes, listens on this machine only and sends nothing anywhere. A second section is from a headless build of WebKit 27.2 (Playwright's: the engine Safari and the Mac app use, but neither program), driven by hand as the doc describes, at normal speed only: the canvas held 60 frames a second at every size, and SVG held it through 1,999 nodes. When a browser's clock ticks in whole milliseconds, as WebKit's does, the script says so in the section and prints no decimal places. The 1,000-node switch is unchanged. Not measured: Safari itself, the Mac app's web view, Firefox, a window on a real screen, a real slow device, radial layouts. The benchmark page and script have no tests of their own.
- Payload plugin docs: moving a departed person's proposals to another account. The README's "When someone leaves" now says that `author` and `decidedBy` can't be changed through Payload, that the lock is a hook and so doesn't cover a host's own database code, and that a host making that move there must change only those two fields and leave `proposal`, `checksum` and the snapshot alone. A new test makes the move on MongoDB and checks that the proposal still matches its checksum, the version made from it still verifies, and the proposal stays locked. No code changed; an option to allow the move through Payload was considered and not built (ADR 0012).
- Payload plugin: people are recorded by id, never by name (changes the unreleased proposals, before anyone used them). `proposals.nameOf` is gone. `proposals.personId({ req })` gives an opaque id for the signed-in person (default: their user document's id), and that id is all a proposal stores about its author and all an accepted proposal seals into the new snapshot for the author and the manager. An id is 1 to 64 letters, digits, `.`, `_`, `:` and `-`, starting with a letter or digit, so an email address or a name with a space in it is refused: the action stops, nothing is saved, and the refused value isn't written to the log. A one-word handle would pass; the plugin can't tell it from an id. `proposals.displayName({ req, personId })` is optional and gives the name to show: it is looked up each time a proposal is read (once per person per request), returned as `authorName` on the proposal and in the preview, and never stored or sealed, so a name changed or removed at the site changes what is shown at once and leaves every snapshot's checksum alone. Why: a name inside a sealed snapshot can't be taken out when a person leaves. Core is unchanged apart from its comments and one error text: `acceptIntoSnapshot` still seals the `author` and `acceptedBy` strings it is given. Still sealed as written, and not screened: a proposal's title, each move's note and the manager's note. No endpoint turns an id from a snapshot's record back into a name. Tested on Payload 3.93 with an in-memory MongoDB (142 plugin tests, 526 in all) and through the example site (47 checks); eight deliberate breaks of the new code each failed a test. Not tested: Postgres or SQLite, and a host with more than one auth collection.
- React: names in the drawing are no longer struck through or covered. In rectangular layouts an inner node's name was drawn 6 units above the node, so when its children's rows were one row apart, a child's branch ran straight through it ("Reptilia" in the amniotes classes view). The name now goes in the first of three places the branches to its children leave clear: on the node's own row, just above it, or just below it; when rows are closer than a name is tall, it takes the place with the most room. A folded branch's name started 8 units out, on top of its 12-unit triangle; it now starts 16 units out, past it. The SVG and the canvas use the same rule (`innerLabelAt`, `leafLabelX`), so a name is in the same place in both. A leaf's name hasn't moved. Limits: a long name can still cross a branch further down the tree, since only the node's own children are looked at, and in a radial drawing a folded branch's triangle still points right whatever the branch's angle.
- Example site: `apps/payload-example`, a small Payload 3.93 and Next.js 16 site that uses the Payload plugin (private, never published). It runs on this machine only, on a throwaway in-memory MongoDB that `pnpm dev` starts and seeds: two made-up accounts with a password made up per run, one published snapshot with two views, and one staged snapshot, all from the repository's illustrative fixtures. Accounts have two roles: a curator manages and decides, a member reads and proposes, only a curator hands out roles, and a member sees no account but their own. Proposals record people by account id, and `proposals.displayName` looks up a public `handle`, not the email address, when one is shown. The public pages are Server Components that read as an anonymous visitor and draw each published view with `TreeView` and `TreeOutline`, with what the view leaves out and its sources; a source's address is a link only when it is http or https. `pnpm smoke` builds the site, starts it on a free port and runs 47 checks over HTTP with sign-in cookies: what a visitor reads and can't do through the pages, REST and GraphQL; cookies that count only from the site's own pages; roles; a proposal made, shared, accepted into a staged, sealed version that records both people by id and holds no handle and no email address. CI runs it, and the CI workflow now cancels a run when a newer push arrives and stops a job after 20 minutes. Passed on `next dev` and on the built site on a Mac; the pages were looked at in headless Chrome in light and dark. Not tested: a person clicking through the admin, a screen reader, Postgres or SQLite, a deployed site. The site has no pages for proposals or imports.

- Payload plugin: tests over HTTP. Twelve new tests send real requests through Payload's own REST router (`handleEndpoints`), signed in with a token from `/api/users/login`: every plugin endpoint is routed and reads its parameters from the URL and the body, the standard routes list a reader only their tenant's published snapshots, another tenant and an anonymous or bad-token request get 404 or 403 and no data, a read route takes no write, a new proposal is its sender's whatever the body says, and accept and decline work from a request body. No code changed. Still not run in a real site behind a web server.
- Payload plugin, part 4 of M7: proposals (still not on npm). With the new `proposals` option, a `taxonomy-proposals` collection holds each signed-in person's own proposals over a snapshot. A proposal is private until its author shares it with the people in their tenant who can read; anonymous visitors never see one. Only the author edits it, and only while it is private. A manager accepts or declines a shared proposal through `POST /api/taxonomy-proposals/:id/accept` and `/decline`, and anyone who can read it gets what it would change from `GET …/:id/preview`. Accepting names the new version and the proposal's checksum as last seen, so a proposal that changed in between is refused. It makes a **new staged snapshot version** and never edits the published one; readers see nothing until a manager publishes it. Two managers accepting at once store one version. The author, the snapshot, the tenant and the decision can't be set through an update, by server code either, and an accepted proposal can't be changed or deleted. Deleting the staged version before it is published opens the proposal again. A third access callback, `access.propose`, says who may propose (default: signed-in users). An accepted version records its author and the manager by person id, not by name (see the entry above). Limits: each acceptance is made from the published snapshot alone; without database transactions a crash between the two writes can leave a staged version to delete by hand; there is no interface yet (a proposal is a JSON field in the admin). ADR 0012, point 15. Tested on Payload 3.93 with an in-memory MongoDB, with and without transactions (127 plugin tests at the time); not through Payload's HTTP routing, in a real site, or on Postgres or SQLite.
- Core: `acceptIntoSnapshot(base, proposal, { version, createdAt, acceptedBy, note })` turns a proposal on a classification into a new, unsealed snapshot version. The base isn't changed. The classification's version becomes `<its version>+<proposal id>`, each moved placement names the new source record `proposal:<id>` as its provenance with where it was before, that record says who proposed and who accepted, and `derivedFrom` pins the base (id, version, checksum) and the proposal (new `derivedFrom.proposal`, type `AcceptedProposal`, in the JSON Schema too). It refuses a base that isn't sealed or fails its checksum, the base's own version, a proposal that moves nothing or was already accepted into the dataset, anything `applyToClassification` refuses, and every proposal on a phylogeny: a tree rearranged by hand is a result its study never found, so a new analysis is imported as its own hypothesis instead. `proposalSourceId` is exported.

- Payload plugin, part 3 of M7 (still not on npm). One run at a time: a run now claims its import job with one conditional update on the job's `attempts` counter, so when several runs of a job start at the same moment one runs it and the others get a 409 and change nothing. Before, both could proceed and one could fail on the unique index. On MongoDB the claim is a single `findOneAndUpdate`; it hasn't been checked on Postgres or SQLite, and a run still working after `staleAfterMinutes` can still be taken over. Views: every view read through Payload itself (REST, GraphQL, the Local API) has a `source` field, `{ doc, id, version, checksum, status, withdrawn }`, the same object the projection and export endpoints give, so a view says its snapshot was withdrawn wherever it is read. It isn't stored, a `source` sent with a view is ignored, it is `null` when the snapshot is gone, and a page of views reads each snapshot's status once. The withdrawn snapshot itself stays hidden from readers. ADR 0012's point 14 (a published view of a withdrawn snapshot stays readable and is flagged) was accepted by the area lead. `@payloadcms/graphql` is a dev dependency for the tests only. Tested on Payload 3.93 with an in-memory MongoDB, through the Local API and a real GraphQL query; not through Payload's HTTP routing, in the admin, or in a real site.
- Payload plugin, part 2 of M7 (`@captiveorigins/payload-plugin-onetaxonomy`, still not on npm; the Release workflow still skips it). Import jobs: with the new `imports` option, a `taxonomy-imports` collection takes a file from the host's upload collection, or a URL through a `fetch` the host passes (nothing is fetched otherwise), runs the matching OneTaxonomy adapter (CSV/TSV checklist, Darwin Core Archive, OneTaxonomy JSON, Newick, NEXUS, phyloXML), seals the result with core's `sealSnapshot`, checks the checksum, validates it and stores it as a staged snapshot. The job records its progress, the adapter's warnings and diagnostics with the line or position. A malformed file or a dataset with validation errors fails the job and stores nothing. The same file with the same settings stores nothing new and says "already imported". An interrupted job can be run again after `staleAfterMinutes` and starts from the file, and one that stopped after storing finds its own snapshot instead of storing it twice. Only managers, in their own tenant, can make, see or run jobs, and a job's input and results can't be edited. Jobs run when made, or through `POST /api/taxonomy-imports/:id/run` and `runImport`. Read API: `coverage` (core's `getCoverageReport`) and `export` (the sealed snapshot as stored) on snapshots, `projection` (core's `projectView` with `describeView`'s disclosure) and `export` on views, with part 1's access, limits and 404 rules. ADR 0012, point 14: a published view of a withdrawn snapshot stays readable and is flagged (`source.withdrawn`, and a "Source withdrawn" disclosure line), never silently hidden. Tested on Payload 3.93 with an in-memory MongoDB and a host fetch answered from memory; not run in a real site, through HTTP routing, with cloud upload storage or over a real network.

- React explorer: the drawing follows the outline's selection (ADR 0010's follow-up, K495). Choosing a taxon in the outline pans the drawing, SVG or canvas, when the taxon is off screen or within 40 px of the edge, and only then, the shortest way. With several taxa selected it keeps them all in view, zooming out only as far as they need; it never zooms in. The pan takes 200 ms, or jumps when reduced motion is asked for or can't be read. Focus stays in the outline, a plain pan announces nothing, and a zoom out says "Zoomed out to show the selection." once (new label `zoomedToSelection`). A click in the drawing doesn't move it, and panning or zooming by hand stops a pan in progress. Tested in jsdom with the frame clock and `matchMedia` stubbed; not tried in a browser, and no screen reader was used.
- Payload plugin, part 1 of M7 (`@captiveorigins/payload-plugin-onetaxonomy` in `packages/payload`, name approved by the owner 2026-11-11, N158; not on npm, and the Release workflow skips it until its first version is published by hand). A `taxonomy-snapshots` collection stores each sealed snapshot whole: one without a checksum, with a checksum that doesn't match, of another schema version or with validation errors is refused, its content can't change afterwards (not even from server code), the same id and version can't be stored twice, and the checksum is checked again when the API first reads it, so a snapshot changed in the database is refused rather than answered from. Snapshots start staged, are published by a signed-in person (recorded), and are withdrawn rather than deleted. A `taxonomy-views` collection holds views that must pin their snapshot's id, version and checksum and pass `validateView`; published views are locked. Read endpoints for name search (exact then prefix, every concept sharing a name listed, common names only in the locale asked for), ancestors, descendants and MRCA run as the requester, cap their results, answer 404 for anything the requester can't read, refuse MRCA on a classification, and answer `indeterminate` in unrooted trees. Access goes through the host's `read` and `manage` callbacks, where only `true` allows; an optional tenant scope keeps tenants apart, cross-tenant reads included. ADR 0012 (proposed) records the design and the later parts. Tested on Payload 3.93 with an in-memory MongoDB; not run in a real site or through Payload's HTTP routing.

- `.onetaxonomy` bundles. When a bundle pins another version of the open dataset, the app asks whether to keep the pinned one (when it's embedded) or relink to the open one; relinking checks every view and lesson first and is refused whole if one doesn't fit. - Linking tree tips to taxa. React: `TipLinker` is a step where a person confirms which taxon each tip of a phylogeny stands for. Each tip's name is matched exactly (letter case aside) against the dataset's taxa and synonyms with core's `findByName`; a match is proposed, never applied. Each tip is accepted, changed to another taxon (several taxa with the same name are all offered, with authorship, rank, source and id), found by another exact name, or left unlinked, and unlinked tips are listed. "Accept all exact unique matches (n)" takes, in one action, only tips with one match by accepted name or synonym; a single misapplied or provisional name waits for a check. One taxon on two tips is flagged, since comparison refuses that. Confirming makes a new phylogeny record with the links in each tip's `concepts` and a `conceptLink` note in its annotations; the record shown is never changed.
