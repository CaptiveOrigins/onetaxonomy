# Changelog

## Unreleased

- Payload plugin, part 4 of M7: proposals (still not on npm). With the new `proposals` option, a `taxonomy-proposals` collection holds each signed-in person's own proposals over a snapshot. A proposal is private until its author shares it with the people in their tenant who can read; anonymous visitors never see one. Only the author edits it, and only while it is private. A manager accepts or declines a shared proposal through `POST /api/taxonomy-proposals/:id/accept` and `/decline`, and anyone who can read it gets what it would change from `GET …/:id/preview`. Accepting names the new version and the proposal's checksum as last seen, so a proposal that changed in between is refused. It makes a **new staged snapshot version** and never edits the published one; readers see nothing until a manager publishes it. Two managers accepting at once store one version. The author, the snapshot, the tenant and the decision can't be set through an update, by server code either, and an accepted proposal can't be changed or deleted. Deleting the staged version before it is published opens the proposal again. A third access callback, `access.propose`, says who may propose (default: signed-in users). `proposals.nameOf` gives the names an accepted version carries. **Those names are sealed into the snapshot and can't be taken out later**, so a site should give a public handle, not an email address. Limits: each acceptance is made from the published snapshot alone; without database transactions a crash between the two writes can leave a staged version to delete by hand; there is no interface yet (a proposal is a JSON field in the admin). ADR 0012, point 15. Tested on Payload 3.93 with an in-memory MongoDB, with and without transactions (127 plugin tests); not through Payload's HTTP routing, in a real site, or on Postgres or SQLite.
- Core: `acceptIntoSnapshot(base, proposal, { version, createdAt, acceptedBy, note })` turns a proposal on a classification into a new, unsealed snapshot version. The base isn't changed. The classification's version becomes `<its version>+<proposal id>`, each moved placement names the new source record `proposal:<id>` as its provenance with where it was before, that record says who proposed and who accepted, and `derivedFrom` pins the base (id, version, checksum) and the proposal (new `derivedFrom.proposal`, type `AcceptedProposal`, in the JSON Schema too). It refuses a base that isn't sealed or fails its checksum, the base's own version, a proposal that moves nothing or was already accepted into the dataset, anything `applyToClassification` refuses, and every proposal on a phylogeny: a tree rearranged by hand is a result its study never found, so a new analysis is imported as its own hypothesis instead. `proposalSourceId` is exported.

- Payload plugin, part 3 of M7 (still not on npm). One run at a time: a run now claims its import job with one conditional update on the job's `attempts` counter, so when several runs of a job start at the same moment one runs it and the others get a 409 and change nothing. Before, both could proceed and one could fail on the unique index. On MongoDB the claim is a single `findOneAndUpdate`; it hasn't been checked on Postgres or SQLite, and a run still working after `staleAfterMinutes` can still be taken over. Views: every view read through Payload itself (REST, GraphQL, the Local API) has a `source` field, `{ doc, id, version, checksum, status, withdrawn }`, the same object the projection and export endpoints give, so a view says its snapshot was withdrawn wherever it is read. It isn't stored, a `source` sent with a view is ignored, it is `null` when the snapshot is gone, and a page of views reads each snapshot's status once. The withdrawn snapshot itself stays hidden from readers. ADR 0012's point 14 (a published view of a withdrawn snapshot stays readable and is flagged) was accepted by the area lead. `@payloadcms/graphql` is a dev dependency for the tests only. Tested on Payload 3.93 with an in-memory MongoDB, through the Local API and a real GraphQL query; not through Payload's HTTP routing, in the admin, or in a real site.
- Payload plugin, part 2 of M7 (`@captiveorigins/payload-plugin-onetaxonomy`, still not on npm; the Release workflow still skips it). Import jobs: with the new `imports` option, a `taxonomy-imports` collection takes a file from the host's upload collection, or a URL through a `fetch` the host passes (nothing is fetched otherwise), runs the matching OneTaxonomy adapter (CSV/TSV checklist, Darwin Core Archive, OneTaxonomy JSON, Newick, NEXUS, phyloXML), seals the result with core's `sealSnapshot`, checks the checksum, validates it and stores it as a staged snapshot. The job records its progress, the adapter's warnings and diagnostics with the line or position. A malformed file or a dataset with validation errors fails the job and stores nothing. The same file with the same settings stores nothing new and says "already imported". An interrupted job can be run again after `staleAfterMinutes` and starts from the file, and one that stopped after storing finds its own snapshot instead of storing it twice. Only managers, in their own tenant, can make, see or run jobs, and a job's input and results can't be edited. Jobs run when made, or through `POST /api/taxonomy-imports/:id/run` and `runImport`. Read API: `coverage` (core's `getCoverageReport`) and `export` (the sealed snapshot as stored) on snapshots, `projection` (core's `projectView` with `describeView`'s disclosure) and `export` on views, with part 1's access, limits and 404 rules. ADR 0012, point 14: a published view of a withdrawn snapshot stays readable and is flagged (`source.withdrawn`, and a "Source withdrawn" disclosure line), never silently hidden. Tested on Payload 3.93 with an in-memory MongoDB and a host fetch answered from memory; not run in a real site, through HTTP routing, with cloud upload storage or over a real network.

- React explorer: the drawing follows the outline's selection (ADR 0010's follow-up, K495). Choosing a taxon in the outline pans the drawing, SVG or canvas, when the taxon is off screen or within 40 px of the edge, and only then, the shortest way. With several taxa selected it keeps them all in view, zooming out only as far as they need; it never zooms in. The pan takes 200 ms, or jumps when reduced motion is asked for or can't be read. Focus stays in the outline, a plain pan announces nothing, and a zoom out says "Zoomed out to show the selection." once (new label `zoomedToSelection`). A click in the drawing doesn't move it, and panning or zooming by hand stops a pan in progress. Tested in jsdom with the frame clock and `matchMedia` stubbed; not tried in a browser, and no screen reader was used.
- Payload plugin, part 1 of M7 (`@captiveorigins/payload-plugin-onetaxonomy` in `packages/payload`, name approved by the owner 2026-11-11, N158; not on npm, and the Release workflow skips it until its first version is published by hand). A `taxonomy-snapshots` collection stores each sealed snapshot whole: one without a checksum, with a checksum that doesn't match, of another schema version or with validation errors is refused, its content can't change afterwards (not even from server code), the same id and version can't be stored twice, and the checksum is checked again when the API first reads it, so a snapshot changed in the database is refused rather than answered from. Snapshots start staged, are published by a signed-in person (recorded), and are withdrawn rather than deleted. A `taxonomy-views` collection holds views that must pin their snapshot's id, version and checksum and pass `validateView`; published views are locked. Read endpoints for name search (exact then prefix, every concept sharing a name listed, common names only in the locale asked for), ancestors, descendants and MRCA run as the requester, cap their results, answer 404 for anything the requester can't read, refuse MRCA on a classification, and answer `indeterminate` in unrooted trees. Access goes through the host's `read` and `manage` callbacks, where only `true` allows; an optional tenant scope keeps tenants apart, cross-tenant reads included. ADR 0012 (proposed) records the design and the later parts. Tested on Payload 3.93 with an in-memory MongoDB; not run in a real site or through Payload's HTTP routing.

- `.onetaxonomy` bundles. Import: `writeBundle` and `readBundle` write and read a ZIP holding `manifest.json` (format version 1, when and by what it was made, each file's size and SHA-256, and the snapshots its views and lessons were made with, pinned by id, version and checksum), an optional embedded sealed snapshot, views, lessons and media, all plain JSON or the media's own format, so `unzip` reads it (format in `docs/architecture/bundle-format.md`). `readBundle` checks everything before returning anything and names each problem with its file: not a ZIP, no manifest, bad JSON, an unknown format version, a missing file, a size or checksum mismatch, a snapshot that isn't the one pinned, a view pinned to nothing, a path outside its folder. A damaged bundle is refused whole. `writeZip` and `crc32` are exported, and core gains `sha256Bytes`. Mac app: Save as bundle… asks whether to include the dataset, lists what goes in and anything that will point to the version on screen, and saves with the same temporary-file-and-rename path as other saves (Cancel writes nothing, and the opened file is never written over); Open… reads `.onetaxonomy` files, with problems in the alert region and what was open left as it was. When a bundle pins another version of the open dataset, the app asks whether to keep the pinned one (when it's embedded) or relink to the open one; relinking checks every view and lesson first and is refused whole if one doesn't fit. Lessons and media are carried through but not shown yet. The app may now write binary files (`fs:allow-write-file`), which a test checks. No SQLite: ADR 0011 (proposed) says why plain files and the bundle cover M6's persistence needs, and what would change that. Tested with Tauri mocked and the system `unzip`; not tried in the built app, and no screen reader was used.
- React: a canvas renderer for large trees. `TreeView` draws SVG up to 1,000 drawn nodes and a canvas above that (`renderer="auto"`, the default; `canvasThreshold` changes the number, and `renderer="svg"` or `"canvas"` forces one). The canvas uses the same layouts, highlight shapes and colors, and the same title and description as the SVG; it is one `role="img"`, and the outline stays the keyboard path (ADR 0010). Level of detail: names and support values are drawn only when their text would be at least 9 px tall and doesn't overlap one already placed (in radial layouts, when the next leaf is far enough away); the selection's name is always drawn. A subtree whose leaves would sit within one pixel is drawn as one wedge, and one holding a highlight shows it. What that leaves out is counted and said in the description and in a visible note ("891 branches are too small to draw at this zoom and are shown as wedges holding 18,218 nodes. …", for a made-up tree of 10,000 tips). Clicks are hit-tested, so selecting, double-clicking to fold and dragging work as on the SVG, and the canvas is drawn at the screen's pixel density. In the explorer, PNG download draws the canvas with the disclosure underneath; SVG download on a canvas tree says why it isn't available instead of doing nothing. `planCanvas`, `prepareTree`, `hitTest`, `drawPlan` and `describeLod` are exported for other renderers. `onNodeClick`'s event is now `MouseEvent<Element>`, since it can come from the canvas. Below the threshold the SVG is unchanged (a snapshot test holds it). Benchmarks of the planning steps in Node are in `docs/benchmarks.md`; nothing has been run in a browser yet, so paint time and smoothness are unmeasured.

- Linking tree tips to taxa. React: `TipLinker` is a step where a person confirms which taxon each tip of a phylogeny stands for. Each tip's name is matched exactly (letter case aside) against the dataset's taxa and synonyms with core's `findByName`; a match is proposed, never applied. Each tip is accepted, changed to another taxon (several taxa with the same name are all offered, with authorship, rank, source and id), found by another exact name, or left unlinked, and unlinked tips are listed. "Accept all exact unique matches (n)" takes, in one action, only tips with one match by accepted name or synonym; a single misapplied or provisional name waits for a check. One taxon on two tips is flagged, since comparison refuses that. Confirming makes a new phylogeny record with the links in each tip's `concepts` and a `conceptLink` note in its annotations; the record shown is never changed. Focus moves to the step's title, and each decision is announced in a status region. `proposeTipLinks` and `linkedPhylogeny` do the same without the UI. Mac app: "Link tips to taxa…" opens the step for the tree shown, and "Add tree…" brings a Newick, NEXUS or phyloXML file into the open checklist or snapshot, so a tree opened alongside its taxa can be linked and then compared. Both add to a new, unsealed snapshot; Save snapshot… suggests a `-linked` (or `-with-trees`) name and refuses every file the dataset came from.
- React explorer: a support threshold field ("Collapse support below", applied on Enter or leaving the field, with a Clear button) collapses low-support branches and says what it did in a status region: "3 branches below 70 collapsed; 2 have no support value." It's disabled for classifications, with the reason beside it. A "Compare with…" panel appears when another phylogeny is loaded or given (`compareWith`): Robinson-Foulds raw and normalized, tips in only one tree, the clades or splits that differ (each clade in the shown tree can be selected), and the reason when the trees can't be compared. With `onRooted`, "Midpoint root" and "Root on this tip/clade (outgroup)" make a new rooted record and hand it to the host; the record shown never changes. A rooted record's `rooting` note is shown under the toolbar and in About, exports and prints.

What the reader skipped is listed in the notes with its line, and rooting that a file leaves unsaid is asked, not guessed. Comparison in the Mac app refuses trees whose tips aren't mapped to taxa, which includes every Newick, NEXUS and phyloXML file it opens, since it never maps tips by label.
- Core: `comparePhylogenies(a, b)` gives the Robinson-Foulds distance (raw and normalized) between two hypotheses on the tips they share, and lists the splits or clades each has that the other lacks. Tips are matched only through explicit concept mappings; tips in only one tree are listed, not dropped. It compares unrooted unless both are explicitly rooted, and refuses unmapped or ambiguous tips and forests.
- Core: `rerootPhylogeny` (on an outgroup of one or more tips) and `midpointRoot` (only when called) make a new phylogeny record whose `rooting` says the method, the outgroup and the record it came from. The input is never changed. Support stays with its split when branches turn around. `Phylogeny.rooting` gains optional `outgroup` and `from` fields, in the JSON Schema too.
- Core: the `collapseBelowSupport` view action draws branches with support below a threshold as polytomies. The projection lists them (`supportCollapse`, `counts.supportCollapsed`) and `describeView` discloses them. The hypothesis keeps every branch, and branches with no support value are never collapsed.

## Mac app 0.2.0

The Mac app with the work listed under Unreleased above (the npm packages are released separately). In the app:

- **Save as bundle… and open `.onetaxonomy` bundles:** your checklist, trees, views and lessons in one documented ZIP with checksums; damaged bundles are named problem by problem, never half-loaded; a different version of the open dataset asks whether to keep or relink (ADR 0011: plain files, no SQLite).
- **Trees:** open NEXUS and phyloXML; add a tree to the open checklist; link its tips to taxa (exact matches proposed, near names offered separately, nothing linked without your yes); compare two trees; reroot on a tip, a clade or the midpoint as a new record; collapse weak branches with the count shown.
- **Large trees** draw on a canvas above 1,000 nodes, with what's too small to draw counted on screen.
- **Accessibility:** contrast fixes, keyboard paths without dragging, toolbars you move along with the arrows, focus moved to forms and errors announced, and a darker focus ring on light backgrounds (owner, 2026-11-11).
- **Saving:** a failed save removes its temporary file or says it couldn't; an unsealed snapshot says so when opened.

Not yet tried in the built app: saving and reopening a bundle, opening a damaged one, and a VoiceOver pass (owner tests). The app is unsigned: see the README for how to open it.

## Mac app 0.1.1

Fixes saving in the Mac app. 0.1.0 wasn't given permission to rename its temporary file over the chosen one, so a save very likely failed and left a `.tmp` file beside it. That was missed because the app's tests run without Tauri's permission checks. Nobody has saved with a built 0.1.0 or 0.1.1 yet: please try a save after installing.

- Mac app: opening a snapshot with no checksum now says it isn't sealed, so a sealed file whose checksum line was deleted no longer opens silently. Saving can now rename its temporary file over the chosen one (the app wasn't allowed to before, so saves failed), and a failed save removes the temporary file, or says it couldn't.
