# 0012 — The Payload plugin stores sealed snapshots whole and answers bounded questions about them

**Status.** Accepted by Science (the area lead), 2026-11-11, within the plugin the owner approved by name (N158). Part 2 (2026-11-11) adds points 12 to 14, built and tested; the lead accepted point 14 the same day. Part 3 (2026-11-11) makes claiming an import job one atomic update (point 12) and carries point 14's flag into Payload's own reads of a view. Part 4 (2026-11-11) adds proposals (point 15), built and tested, with core's `acceptIntoSnapshot`. Part 5 (2026-11-11) adds the admin panels and a snapshot's summary (point 16), built and tested. Later parts are listed below.

**Context.** M7 asks for a Payload plugin with configurable slugs, locale, permissions, an optional tenant scope and source adapters; admin views; a bounded read API with access checks and cross-tenant denial tests; resumable, idempotent import jobs; an example app; and per-user proposals a curator accepts into a new staged version. OneTaxonomy's records are immutable, checksummed snapshots ([data schema](../data-schema.md)), views pinned to them ([ADR 0006](0006-view-actions.md)), and a core that runs anywhere and knows nothing of Payload ([ADR 0002](0002-pure-core.md)). The sister plugins for OnePedigree and OnePhylogeny already set the house pattern: the plugin adds its own collections, takes the host's access rules, refuses what it can't check, and is tested on a real Payload with an in-memory MongoDB.

**Decision.**

1. **Snapshots are stored whole, one document each.** A `taxonomy-snapshots` document holds the sealed `DatasetSnapshot` in a JSON field, exactly as given, beside fields copied from it for lists and queries: `snapshotId`, `version`, `checksum`, a label and counts. Concepts, names, classifications and phylogenies are not split into Payload documents: the architecture already says large topologies are stored as whole snapshot records, not millions of CMS documents, and splitting them would make the checksum a claim about data spread over many writes.
2. **Sealed means sealed.** On create the plugin refuses a snapshot without a checksum (it never seals for the caller: the checksum is the producer's claim), one whose checksum core's `verifySnapshot` rejects, one of another schema version, and one with `validateDataset` errors. Its content can't change after that, in any status and even for trusted server code: the check is in a hook, not in access. A changed dataset is a new version, and the same id and version can't be stored twice in a tenant (a compound unique index backs the hook's check).
3. **The checksum is checked again when read.** The read API recomputes the checksum the first time it loads a stored snapshot, and answers 500 with a plain reason if it no longer matches, so a database edit behind Payload's back is refused, not answered from. Indexes are cached per document and checksum (eight at a time), which is safe because the content can't change; access is checked on every request before the cache is used.
4. **Staged versions.** A snapshot starts `staged` and moves to `published`, then `withdrawn`; staged may also be withdrawn. Nothing moves back. Publishing needs a signed-in person, and the plugin records who and when. Only staged snapshots can be deleted; a published one may be pinned by views and pages, so it is withdrawn instead, which hides it from readers and keeps it for managers.
5. **Views are pinned and checked.** A `taxonomy-views` document relates to one snapshot and holds a `TaxonomicView` that must pin that snapshot's id, version **and** checksum; core's `validateView` must find no errors. Views start as drafts, can be changed while drafts (and are checked again), and are locked once published. A view can be published only over a published snapshot, and no new view can use a withdrawn one.
6. **The host decides who, through two callbacks, and they fail closed.** `access.read` (default: signed-in users) and `access.manage` (default: nobody, so only trusted server code using the Local API with `overrideAccess`) get `{ req, tenant }`. Only `true` is a yes: `false`, a truthy value that isn't `true`, or a throw is a no. Managers see every status in their tenant; readers see only published records in their tenant. The plugin turns these answers into Payload access results, so the REST, GraphQL and Local APIs all keep them.
7. **Tenant scope is optional and absolute.** With `tenant: { collection, field?, resolve }`, both collections get a required relationship to the host's tenants collection. `resolve({ req })` gives the requester's tenant; null, an unusable value or a throw means no access at all. A new record gets the maker's tenant, naming another tenant is refused, the tenant can't change afterwards (even for trusted code), and a view can only use a snapshot in its own tenant. A person who works for several tenants is the host's to resolve per request.
8. **The read API is bounded and answers 404 for anything unreadable.** `GET /api/<snapshots>/:id/search`, `/ancestors`, `/descendants` and `/mrca` run as the requester. A snapshot that doesn't exist, isn't readable to them, belongs to another tenant, or an id that isn't valid all answer the same 404, so a caller can't learn that a hidden snapshot exists; an unknown hierarchy or node is 404 too. Results are clamped to `limits` (defaults: 100 results, depth 100, 100 MRCA nodes) and say when they were `truncated`. The same functions (`searchNames`, `ancestorsOf`, `descendantsOf`, `mrcaOf`) are exported for host pages, taking a `req`.
9. **The science rules carry through.** Search returns every concept that uses a name, so homonyms and splits stay separate (I10); synonyms say they are synonyms. Common names are searched only in the locale asked for (`?locale=`, else the plugin's `locale.default`; without either, only scientific names). Ancestors and descendants of a node in an unrooted phylogeny answer `indeterminate` (`unrooted`), not storage order (I5). MRCA is core's `findMRCA`, naming the hypothesis; a classification is refused with a reason (I2), and a forest gives `none` (I8).
10. **Core stays free of Payload.** Only `packages/payload` depends on `payload` (a peer dependency, `^3.80.0`). Core, import, layout, react and education neither depend on nor import it, and a test in the plugin checks that. The plugin depends on core, since part 2 on import for its adapters, and since part 5 on react for the drawing in the view panel. It holds no taxonomic data and fetches nothing by itself: an import reads a URL only through a `fetch` the host passes, which decides what is allowed ([ADR 0005](0005-source-ownership.md)).
11. **License and release.** PolyForm Noncommercial 1.0.0 with the `Required Notice`, like every OneTaxonomy package ([ADR 0009](0009-license.md)). The version moves in lockstep with the others ([ADR 0007](0007-releases.md)), but the Release workflow doesn't stage it: the owner publishes its first version by hand, as with each package's first version, and it is added to the workflow once trusted publishing is set up for it.

12. **Import jobs are a collection of their own, not Payload's jobs queue.** With the `imports` option, a `taxonomy-imports` collection holds one document per job: the format (`csv`, `dwca`, `onetaxonomy-json`, `newick`, `nexus`, `phyloxml`), one input (a document of the host's upload collection, or a URL), plain JSON settings, and what the run did: status (`queued`, `running`, `done`, `already-imported`, `failed`), phase, progress lines, the adapter's warnings, diagnostics, the input's SHA-256, the checksum and the snapshot made or found. Payload's jobs queue was not used: registering a task adds a `payload-jobs` collection to every host, its tasks run with access skipped, and its retries would repeat a run the job record already describes. A host that wants a queue calls `runImport` from its own task.
    - **Running.** A job runs when it is made, in the same request, as its maker (`imports.runOnCreate`, default on), or later through `POST /api/<imports>/:id/run` or `runImport(req, id)`. Only managers in the job's tenant can make, see or run a job; everyone else gets the same 404 as for a missing one. Server code without a user passes `overrideAccess`. An uploaded file is read as the person running the job, so the host's upload access applies; a URL is read only through the host's `fetch`, and without one a job can't name a URL. Input past `imports.maxBytes` (default 15 MB) is refused.
    - **Sealed and checked.** The adapter's result goes through core's `toSnapshot`, `sealSnapshot` and `verifySnapshot`, then `validateDataset`; any error stops the job with every diagnostic and nothing stored. A sealed OneTaxonomy JSON file is kept as sealed, and one that fails its checksum is refused. Tree labels map to concepts only through an explicit `labels` table.
    - **Idempotent.** `settings.snapshot.createdAt` is required, because it is part of the checksum: the same file with the same settings gives the same checksum. A job that finds the same id, version and checksum already stored in its tenant links it and ends `already-imported`, storing nothing; the same id and version with another checksum fails ("a changed dataset needs a new version"). Running a finished job again changes nothing. A job's input and results can't be edited after it is made, even by server code; only its title can.
    - **Never half a snapshot.** The snapshot is stored last, as one document, after every check passed, so a run that stops leaves either no snapshot or a whole one. A job left `running` is refused (409) until `imports.staleAfterMinutes` (default 15) have passed, then starts again from the file. If it had stopped after storing, the re-run finds its own snapshot by checksum and finishes `done` without storing it twice.
    - **One run at a time.** A run starts by claiming the job with one conditional update: it succeeds only if the job's `attempts` counter is still what the run read, and it adds one. Every run that starts moves the counter, so when several start together one claims the job and the rest get a 409 and change nothing. On MongoDB the check and the write are a single `findOneAndUpdate`; inside a transaction the loser gets MongoDB's write conflict, which is answered with the same 409. The claim is written straight through the database adapter, because Payload's `update` reads and then writes. Limits: it hasn't been checked on Payload's SQL adapters, where the unique index on a snapshot's id and version is still the backstop; and it guards the start only, so a run still working after `staleAfterMinutes` can be taken over and will write its own progress lines when it wakes. The two can't both store a snapshot.
13. **The rest of the bounded API.** `GET /api/<snapshots>/:id/coverage` runs core's `getCoverageReport` for a classification, optionally a phylogeny, listed groups and a listed selection (every concept when none is listed), capped by `limits.maxResults` groups and `limits.maxCoverageIds` concepts, and says knowledge of what science knows is not stated. `GET …/:id/export` downloads the sealed snapshot exactly as stored, after the checksum check. `GET /api/<views>/:id/projection` runs core's `projectView`, capped at `limits.maxNodes` (default 5,000) with `truncated`, and returns `describeView`'s disclosure beside it; `GET /api/<views>/:id/export` downloads the view file with the snapshot it pins and the disclosure lines. All of them run as the requester with part 1's rules: readers see published records, managers every status, all in their tenant, and anything else is the same 404. A view's snapshot is read through the view, and must still match the pin and its checksum, or the answer is a 500 with the reason.
14. **Accepted by Science (the area lead), 2026-11-11: withdrawing a snapshot doesn't hide its published views.** A published view of a withdrawn snapshot stays readable, and every answer about it carries the flag: `source.status: 'withdrawn'`, `source.withdrawn: true`, and a first-class disclosure line ("Source withdrawn: snapshot … was withdrawn by its publisher after this view was published. …") in projections and exports. The snapshot itself stays hidden from readers, as point 4 says. Why: views are cited and linked; hiding them silently breaks those links and hides that something changed; saved references are never rewritten or dropped silently (I18). A flag keeps the change visible. The alternative, hiding the views, was one access rule away and wasn't chosen.
    - **Payload's own reads carry it too (part 3).** A view has a `source` field that isn't stored: it is worked out each time the view is read, from the snapshot's head, and is the same object the endpoints answer with (`doc`, `id`, `version`, `checksum`, `status`, `withdrawn`). So a view read over REST, GraphQL or the Local API says its snapshot was withdrawn without a second request. It is null when the snapshot is gone. A `source` sent with a view is ignored. The snapshot's status is read once per request for each snapshot, and read again if the snapshot changes in that request. Populating the view's `snapshot` relationship still gives readers only its id once it is withdrawn, as point 4 says.

15. **Proposals are people's own, and accepting one makes a new staged version (part 4).** With the `proposals` option, a `taxonomy-proposals` collection holds one document per proposal: the snapshot it is drawn over, core's `Proposal` (title, notes, base, moves), a status, and a checksum of the proposal. The plugin sets the proposal's id, author (a person id) and date; anything else sent with it is dropped.
    - **Whose and who sees.** A proposal belongs to the signed-in person who made it. They need the host's `read` answer and a third callback, `access.propose` (default: signed-in users; only `true` is a yes). Proposals are never shown to anonymous visitors, even on a site whose snapshots are public. A proposal is `private` (seen by its author only), `shared` or `accepted` (seen by everyone in the tenant who may read), or `declined` (seen by its author and managers). Readers see that a proposal was accepted, with the manager's note and the date, but not who decided or the staged version it made: those two fields are for managers. The snapshot is read as the requester, so a snapshot that is missing, hidden or in another tenant gives one answer, and a proposal can't be used to find out that a hidden snapshot exists.
    - **Sharing locks it.** Only the author edits a proposal, and only while it is private. Sharing needs at least one move and a published snapshot. To change a shared proposal its author takes it back to private first, so what a manager looks at can't change under them without the checksum changing. The author, the snapshot, the tenant and the decision fields can't be set through an update, by anyone, trusted server code included: the checks are in a hook.
    - **A manager decides, through two actions.** `POST /api/<proposals>/:id/accept` and `/decline` (and `acceptProposal`, `declineProposal`) work for managers in the proposal's tenant; everyone else gets the 404 of a missing proposal. Accepting names the new version and the proposal's checksum as the manager last saw it (`GET …/:id/preview` gives it, with the taxa moved and the groups changed, broken and formed, bounded by `limits.maxResults`). A proposal that changed since is refused.
    - **Accepting never edits a published snapshot.** Core's `acceptIntoSnapshot` makes an unsealed copy with a new version, in which the classification gets a new version (`<its version>+<proposal id>`), every moved placement names the proposal as its provenance, a source record (`proposal:<id>`) says whose proposal it was and who accepted it, and `derivedFrom` pins the base snapshot's id, version and checksum, and the proposal. The plugin seals it, checks the checksum, validates it and stores it **staged**. Readers see nothing new until a manager publishes it, which is the second look. The base must be published at that moment; a staged, withdrawn or deleted base is refused.
    - **Phylogenies are never accepted.** A proposal on a phylogeny can be made, shared and previewed, as in the explorer, but accepting it is refused in core and in the plugin. A phylogeny is a published hypothesis with a citation; a tree rearranged by hand is a result its study never found, so it can't take that hypothesis's place. A new analysis is imported as its own hypothesis.
    - **Once, and together.** The new snapshot and the proposal's new status are written in one transaction where the database has them. The proposal is claimed with one conditional update (still shared, same checksum), so two managers accepting at once store one version and the other gets a 409, and an author who takes the proposal back in that moment wins: nothing is accepted. Without transactions the new snapshot is deleted again when the claim fails. Declining is the same conditional update without a snapshot.
    - **People are sealed by id, never by name (changed 2026-11-11, before any release).** The first version of this point sealed a name the host chose (`nameOf`, a public handle). That was wrong for a site whose people can ask to be forgotten: a name inside a checksum can't be taken out without making a new version, and a published version may already be pinned and cited. Now `proposals.personId({ req })` gives an opaque id (default: the signed-in user's document id), and only that id is stored on a proposal and, on acceptance, sealed into the new snapshot's source record and `derivedFrom`. An id is 1 to 64 letters, digits, `.`, `_`, `:` and `-`, starting with a letter or digit, so an email address or a name with a space in it is refused; a throw or any other value also stops the action, nothing is saved, and the log line never repeats the value. The pattern can't tell a one-word handle from an id, so the docs say not to give one. A name is shown through `proposals.displayName({ req, personId })`, called when a proposal is read (once per person per request) and returned as `authorName`: a field that is computed on read, dropped on write and never in the database. When a name is removed at the host, nothing shown or sealed names the person. The title, each move's note and the manager's note are free text and are sealed as written; the plugin doesn't screen them.
    - **Kept and deleted.** An author can delete their own private and declined proposals. A shared one must be taken back first. An accepted one can't be changed or deleted, even by trusted code, because a snapshot version names it. If the staged version it made is deleted before publishing, the proposal goes back to shared with a note saying so. A host's own code can take back and delete a departed person's open proposals; their accepted ones stay, under their id. The document's `author` and `decidedBy` (the user document's id, as text) can't be changed through Payload. A way to allow it for a host that moves a departed person's records to another account (a flag only server code can set, plus a host check) was considered on 2026-11-11 and not built: the one host that asked makes that move in its own database transaction, where no hook runs, so the option would have had no user. What the plugin owes such a host is that the move is safe, and a test shows it: with only those two fields changed underneath it, the proposal still matches its checksum and the version made from it still verifies, because neither field is inside either checksum. Build the option when a host needs to make the move through the Local API.
    - **Limits.** Each acceptance is made from the published base alone: two proposals accepted on one snapshot give two versions, not one with both. To combine them, publish the first and propose again on it. Without transactions, a crash between storing the snapshot and claiming the proposal can leave a staged version no proposal points to; a manager deletes it. The note from an earlier decision stays on a proposal that is shared again, until the next decision. The conditional update is one statement on MongoDB; it hasn't been checked on Postgres or SQLite. One person keeps at most `maxPerUser` proposals (default 200, not counting accepted ones) of at most `maxMoves` moves (default 500). In the admin a proposal's content is still a JSON field, under its panel (point 16). Only a snapshot's summary (point 16) turns a sealed id back into the name the host shows for it now, and only for a signed-in requester; a visitor gets the ids alone.

16. **The admin panels are a page over the same API, with no powers of their own (part 5).** Each of the plugin's four collections gets a panel at the top of its edit page, on unless `admin: { panels: false }`.
    - **A field on Payload's own edit page, not a custom view.** The panel is a `ui` field. Payload's save button, permissions, versions and the fields under the panel stay as they are, and there is no second edit page to keep in step with Payload. At first the cost was that a snapshot's edit page loaded the whole snapshot into Payload's JSON field below the panel; point 17 takes that away.
    - **Browser code is a separate entry.** The panels are client components in `@captiveorigins/payload-plugin-onetaxonomy/client`, which Payload finds through its import map. `@payloadcms/ui` and `react` are optional peer dependencies, so a host that turns the panels off, or uses the plugin without an admin, needs neither. A test checks that the server entry imports no browser code and the client entry no server code.
    - **Every answer is the site's.** The panels call the host's own site from the browser, as the signed-in person, with their cookie. Publishing and withdrawing are Payload's standard `PATCH` of `status`, asking back only the fields the panel shows, so the answer never carries a snapshot's content. Running an import, accepting and declining are the endpoints of points 12 and 15. Which buttons appear follows Payload's own word on whether this person may save the document; that is a courtesy, and a button shown by mistake still gets the site's 403 or 404. A refusal is shown as "Nothing was changed." with the site's reason.
    - **One new endpoint.** `GET /api/<snapshots>/:id/summary` (and `summarizeSnapshot`) answers what a snapshot holds, small enough for a page: its status, counts, sources with their licenses, a line per classification and phylogeny, and what it was made from. Lists are capped (20 by default, never past `limits.maxResults`) and say when they were cut. It never returns names, concepts or trees. Same access and the same 404 as point 8, after the checksum check of point 3. For a snapshot made from an accepted proposal it gives the two sealed person ids, and beside each the name `proposals.displayName` gives now: for a signed-in requester only, looked up per request, never stored. A visitor who may read the snapshot gets the ids and no names.
    - **Ask first, and say what can't be undone.** Publish, Withdraw, Accept and Decline open a confirm in the page, and nothing is sent before it. Running an import doesn't ask: the most it does is store a staged snapshot, which only managers see and which can be deleted. Publishing and withdrawing say that nothing moves back. Accepting lists what is sealed into the new version for good (the title, the notes and move notes, the manager's note, the date and the two ids) and asks the manager to check that none of it holds personal details, because point 15 doesn't screen free text. Declining says the author will see the note. Accepting sends the checksum the panel showed, so a proposal that changed meanwhile is refused (point 15).
    - **A view's drawing is bounded and has an outline.** The view panel draws the saved view from its projection, cut at 200 nodes and saying so, with the same tree as an outline for the keyboard and the lines readers are told about it. Publish waits, with the reason beside it, until the form is saved and the snapshot is published.
    - **An import's progress is asked for, not pushed.** While a job is running the panel reads its few run fields again every 3 seconds, and stops when it isn't or when the page is left. A job running past `staleAfterMinutes` is called probably interrupted and can be run again; a running one can't be started twice from the panel, and point 12's claim refuses it anyway.
    - **Readable without colour, in Payload's themes.** A status is a word, with a coloured edge beside it; the state colours are used for edges only, never for text. The panels take their colours from Payload's theme variables, and a test reads the installed `@payloadcms/ui` stylesheets and checks text and muted text at 4.5:1 and control edges at 3:1 in the light and dark themes. The drawing's colours are copies of the React package's, kept equal by a test, and switch on Payload's own theme marker, because the admin's theme is the person's choice in Payload and not the system's.
    - **Limits.** Tested in jsdom with Payload's hooks and `fetch` replaced by stand-ins, over HTTP in the example site, and clicked through in headless Chrome on that site by its `click-through` script (all four panels, light and dark, 40 checks), which needs Chrome and the network and so isn't in CI. That script's first run on the import pages found the panel's paragraphs and lists flush against each other in the real admin: the panel's own margin reset outranked its spacing rule, which jsdom can't show. The reset now carries no weight (`:where`), and the script measures the gaps. The form under a panel no longer repeats it: the fields a panel shows are `admin.hidden`, so they stay in the form's data, where the import panel puts a run's result so that a later Save doesn't send the old one. No screen reader, Safari, Firefox or phone was tried. Payload's admin makes two requests of its own to other sites on these pages: its JSON field loads its code editor from cdn.jsdelivr.net (not on a stored snapshot's page, which has no JSON field since point 17), and its default avatar asks gravatar.com with a hash of the signed-in person's email address unless the host sets `admin.avatar: 'default'`. The panels themselves ask only the host's site.

17. **A snapshot's content is read only when it is asked for by name.** A stored snapshot can be 15 MB, and Payload reads whole documents by default: for a list, for a relationship it fills in, and for every admin page.
    - **The rule.** A read, create, update or delete of a snapshot that names no `select` answers with every field except `snapshot`. `select: { snapshot: true }` (REST `?select[snapshot]=true`, GraphQL `select: true`) gives the content. A caller's own `select` is never changed, so an exclude-mode select such as `{ status: false }` still carries the content. The export endpoint and the read API of points 8 and 13 are as before.
    - **Where it is done.** One `beforeOperation` hook on the snapshots collection, which covers REST, GraphQL, the Local API, populated relationships and the admin alike. An `afterRead` hook would be too late (the document is already loaded), and a field-level `access.read` would hide the content from the people entitled to it. This is about weight, not access: whoever may read a snapshot may select its content.
    - **The lock doesn't lean on it.** Point 2 compares an update with the stored document, which Payload reads whole whatever the caller selected. Every place in the plugin that needs the content (the cache of point 3, a view's checks, imports, proposals, the export) selects it by name; a test fails if the view hook stops doing so.
    - **The admin.** The content field is shown on the new-snapshot form only (`admin.condition`), where a manager pastes a sealed snapshot. A stored snapshot's page is sent without the content and without the editor; the panel says what the snapshot holds. Payload's own Save there sends the status and no content. The same condition is what makes the field nullable in GraphQL, so a plain query answers `null` for it instead of failing.
    - **The panels follow Payload's Save.** The panels read their own data from the site, so they went stale when a manager changed the status with Payload's own field and Save. They now read again whenever Payload reports the document saved.
    - **For hosts.** Code that read `doc.snapshot` from a plain read, or from the document an after-read or after-change hook is given, has to select it. The plugin has no release yet, so nothing in use changes.
    - **Limits.** A stored snapshot's content can't be looked at in the admin; the export gives it. Tested on a real Payload with an in-memory MongoDB, over HTTP in the example site, and in headless Chrome on that site by its `click-through` script, which isn't in CI. In an earlier scratch version of that script, after a snapshot was made through the form and its page loaded again, Payload's read-only Counts group once showed its heading with no fields under it; four shorter runs of the same steps drew them, and the cause wasn't found. The form no longer draws that group, because the panel shows the counts (point 16), so it can't be seen again there; a host's own read-only group in a Payload form could still show it. Not checked: Postgres or SQLite, a browser with a window.

**Later parts of M7, not built yet.**

- The rest of the admin views: list views, conflicts, tree authoring, profiles, lessons. Part 5 covers import progress, publishing and a manager's look at a proposal before deciding.
- A page for making a proposal in the admin, and a drawing of one. A proposal is made through the API or in the React explorer; the proposal panel says what it would change in words and tables.
- The panels in a screen reader, Safari, Firefox and on a phone, and a browser run in CI.
- The atomic claims (import jobs, proposals) on Postgres and SQLite, which need those adapters in the tests.
- Very large snapshots. A MongoDB document holds at most 16 MB, so a snapshot past that can't be stored this way (imports refuse past `maxBytes`); the likely answer is the host's upload collection for the JSON, with the checksum kept here.

**Consequences.** One document per snapshot keeps the checksum meaningful and the plugin small, at the cost of loading a whole snapshot to answer the first question about it (later ones use the cache). Locking content in hooks, not access, means even trusted server code can't edit a sealed snapshot; corrections are new versions, which is what views pinning `{ id, version, checksum }` already assume. Hosts must write two callbacks to open anything to anyone, which is deliberate: the defaults show nothing to anonymous visitors and let no one but server code manage. Proposals put two person ids into a sealed record for good, which is what makes an accepted change traceable; who those ids are is answered by the host, for as long as it chooses to.
