# Limitations and risks

Kept current with each milestone. Nothing listed here is claimed as done.

## Current (after M5 part 1)

- Input formats: Newick, NEXUS (TREES blocks only), phyloXML (clades, names, branch lengths, confidence, taxonomy; other elements are reported and skipped), OneTaxonomy JSON, delimited checklists (CSV/TSV) and Darwin Core Archives (Taxon core + Vernacular Names; other extensions are reported and skipped). The NEXUS and phyloXML readers are tested on hand-written files, not yet on exports from MrBayes, BEAST, PAUP, Mesquite or Archaeopteryx. The Mac app doesn't open them yet. phyloXML is read with a small strict XML reader (no DTDs or external entities).
- Darwin Core Archives: no ZIP64, no encryption, CRCs not checked; `meta.xml` is read with a small purpose-built parser (core/extension, files, id/coreid, fields with index or default), not a general XML parser. Very large archives are read into memory.
- Reconciliation links concepts only by shared identifiers and lists same-name candidates; there is no fuzzy matching, authorship parsing or concept-relationship (RCC-5) model yet. Curators link concepts by hand.
- Split/lump detection in `diffSnapshots` is a heuristic over name usage (candidates only) and relies on adapters producing stable ids from the source's own identifiers.
- Coverage counts what a dataset and a hypothesis hold; numbers known to science come only from the caller with a cited source.
- Views, layouts and the React explorer exist (M4) with pan/zoom and drag to reorder; the viewer draws SVG only, so very large visible trees (thousands of nodes) will be slow until the Canvas renderer (M8). `comparePhylogenies` (2026-11-11) gives Robinson-Foulds distances on shared tips only; it ignores support and branch lengths, and refuses trees with unmapped tips or several tips for one concept (choose one sample per concept first).
- Overlays (M5) draw only stated values: support and ages from the hypothesis, life status, and observed trait states. Ancestral or missing trait states are never inferred (a labelled parsimony method is M8). A phylogeny node mapped to concepts with different states shows "mixed".
- Exports: SVG and PNG carry the disclosure under the drawing; PDF is the browser's print to PDF (the printout carries the same disclosure). PNG is rendered in the browser. Embeds: render `TreeView` on a server page (no script needed); there is no hosted embed snippet.
- The JSON Schema (`schema/snapshot.schema.json`) checks structure only; referential integrity and scientific checks stay in `validateDataset`.
- `assessTaxon` maps members to terminals only through explicit `concepts` on phylogeny nodes. Importers must create those mappings; until then, real trees report members as unmapped (by design, I7).
- Support values are shown and weak ones marked (M5 overlay). Views can collapse branches below a support threshold (2026-11-11, core only: the explorer has no control for it yet). Branches without a support value are never collapsed.
- Rooting (2026-11-11): `rerootPhylogeny` (outgroup of tips) and `midpointRoot` make new records and refuse time-calibrated hypotheses. Where the root sits along the outgroup branch is not known from the data; it defaults to halfway and the record says so. Neither is in the explorer or the Mac app yet.
- Index building is in memory. Large-tree benchmarks (10k+ taxa) are planned for M8; traversal is iterative and tested on a 20,000-deep chain.
- Fixtures are illustrative. They mirror widely discussed relationships (turtles with archosaurs) but are not sources and must not be cited.
- The five `@captiveorigins/onetaxonomy-*` packages are on npm as alpha versions (ADR 0008). The Payload plugin isn't published yet.
- Proposed mode on a phylogeny leaves a group with one remaining child in place rather than collapsing it. Moved branches lose their lengths, and groups whose members changed lose their support values and ages, so a proposal is not a tested hypothesis. Highlights keep the assessment of the hypothesis they name. Proposals are stored and shared by the Payload plugin (M7 part 4, 2026-11-11) and in the view file; the explorer and the Mac app don't save them anywhere else. A curator can accept a proposal on a classification into a new snapshot version (`acceptIntoSnapshot`); a proposal on a phylogeny is never accepted, because a tree rearranged by hand is a result its study never found. An accepted proposal's author and curator are named in the sealed snapshot for good.
